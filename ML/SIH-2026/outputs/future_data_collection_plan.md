# Plan for collecting a labelled conveyor dataset

The current model is unsupervised because the current data is unlabelled. This document
describes how to collect a dataset that would justify a supervised fault classifier, and
what that classifier could then legitimately claim.

This file is hand-written, not generated by the pipeline. Do not delete it when clearing
`outputs/`.

Nothing here should be attempted on a loaded production conveyor. Every experiment below
is designed for the bench prototype, at low speed, with the belt clear of people and
hands, and with a person at the power switch.

---

## 0. Fix the acquisition defects first

The data-quality report found four problems that would corrupt a labelled dataset just as
badly as they limit this one. Fix them before spending time on fault runs -- a labelled
dataset with these defects is not worth much more than the unlabelled one.

| # | Defect found in the current recording | Fix before the labelled campaign |
|---|---|---|
| 1 | `ts_ms` stalls: up to ~100% duplicate `(node, ts_ms)` pairs late in the session, while `seq` keeps counting correctly | Stamp each frame from a monotonic microsecond source on the ESP32 (`esp_timer_get_time()`), sampled at acquisition time, not at transmit time. Keep `seq`. Verify: no duplicate `(node, ts_ms)` in a 10-minute run. |
| 2 | USB-serial burst delivery: ~4 frames flushed together every ~2 s | Either flush per frame, or add a device-side `sampled_at_us` so burst delivery stops mattering. Gateway `received_at_ms` is not a substitute -- it has the same bursts. |
| 3 | Hall RPM holds the same value for ~3 s (median 6 frames), so the effective update rate is ~0.33 Hz | Report edge timestamps, or the interval between the last two magnet passes, rather than a slow smoothed RPM. At ~20 RPM with one magnet a revolution takes ~3 s, so add magnets to the drum (4 magnets gives ~0.75 s resolution) if faster RPM updates are needed. |
| 4 | Median segment is ~8 s; 41 of 78 segments are too short to yield even one 10 s window | Record in continuous blocks of at least 3 minutes. Segment fragmentation, not total duration, is what starved this dataset. |

Also worth adding, because their absence blocks whole fault classes:

- **Motor current** (a clamp or in-line shunt). Without it, load and slip are invisible.
  `motor_current_rms`, `motor_power`, `motor_rpm`, `slip_ratio` and `load_cell_kg` are all
  present in the schema and all 100% empty.
- **A second RPM source at the motor shaft.** Slip ratio is by definition motor speed
  versus belt/drum speed; one Hall sensor cannot give it.
- **Accelerometer die temperature**, if the IMU exposes it. Section 6 of the evaluation
  report shows the static acceleration channels drifting with session temperature, most
  likely MEMS thermal bias. Logging die temperature makes that correctable instead of
  confusing.

## 1. Classes to collect

| Label | What it is | How to induce it safely on the prototype |
|---|---|---|
| `NORMAL` | Belt running at the nominal set point, correctly tensioned, unloaded or evenly loaded | No intervention. This is the reference class and needs the most data. |
| `BELT_SLIP` | Belt slipping on the drive drum | Reduce belt tension via the tensioner by a measured number of turns, in small documented increments. Stop at the first sign of slip. Do **not** brake or hold the belt by hand. |
| `HIGH_VIBRATION` | Excess mechanical vibration | Bolt a small eccentric mass to the driven roller or an idler, or deliberately loosen **one** non-structural mounting bolt by a documented amount. Keep the mass small enough that the frame never leaves its feet. Torque everything back after the run. |
| `OVERHEATING` | Drive-side thermal excursion | Do this thermally, not mechanically: run the conveyor with the motor's ventilation path partly restricted, or in a warm enclosure, and stop at a pre-set temperature ceiling. Choose that ceiling from the motor and belt datasheets, not by feel. Never induce heat by stalling the motor. |
| `RPM_INSTABILITY` | Speed not holding its set point | Modulate the drive supply / PWM duty in a controlled pattern from the controller. This is a software-only fault and is the safest one on the list. |
| `COMBINED_FAULT` | Two of the above together | Only after each single fault has been recorded, characterised and shown to be safe on its own. Start with the two mildest. |

**A hard rule:** the current model has never seen the conveyor running at any speed other
than 20.4-20.7 RPM. Before any fault runs, record `NORMAL` across a **range of set-point
speeds** and, if possible, a range of belt loads. Otherwise a classifier will learn "unusual
speed = fault", which is exactly the mistake this project is trying to avoid.

## 2. Recording protocol

**Per run.** One run = one label = one continuous recording.

1. Record 3 minutes of `NORMAL` immediately before the run and 3 minutes immediately
   after, at the same speed. This gives a matched control for that specific session and
   makes thermal drift separable from the fault.
2. Introduce the fault condition in a single documented step. Write down the physical
   quantity: turns of the tensioner, grams of eccentric mass, degrees of enclosure
   temperature, percent PWM deviation.
3. Hold the condition for at least 5 minutes of clean recording.
4. Restore the machine to nominal and confirm the post-run `NORMAL` block looks like the
   pre-run one. If it does not, something changed that was not the intended fault --
   discard the run and investigate.

**Per campaign.**

- **Thermal warm-up must be broken as a confound.** In the current dataset temperature
  correlates with session time at r = 0.96, which makes "hot" and "late" the same thing.
  Randomise the order in which labels are recorded across sessions, and record some faults
  from a cold start and some after an hour of running. Do not record all of one label on
  one day.
- **Aim for at least 30 minutes of clean data per class**, spread over **at least 3
  separate sessions on different days**. Three sessions is the minimum that allows a
  session-held-out split, which is the only split that will honestly answer "does this
  work tomorrow".
- **Vary ambient conditions** where practical -- morning versus afternoon is usually enough
  to move ambient by a few degrees.
- Record severity where it is meaningful: `BELT_SLIP` at 2, 4 and 6 tensioner turns is far
  more useful than `BELT_SLIP` at one arbitrary setting, and it lets a later model estimate
  severity rather than only presence.

**Labelling.** Write the label at recording time, into the session metadata, from the
operator's log -- never inferred afterwards from the signal. Post-hoc labelling by looking
at the vibration trace is circular: it labels the data with the very thing the model is
supposed to discover. Keep the operator log (who, when, what was changed, what was
observed) alongside the CSV.

**Target volume.** Six classes x 30 minutes x 3 sessions is roughly 9 hours of clean
recording. At a 10 s window with a 5 s step that is on the order of 6,000 windows, from
enough distinct sessions to support a real held-out split. For comparison, the present
dataset yields 225 windows from 37 segments of a single session.

## 3. How the labelled dataset would then be used

**Splitting.** Group by *session*, never by window and never by row. All windows from one
session go entirely to train or entirely to test. Anything else leaks: overlapping windows
share raw frames, and windows from one session share one thermal state, one belt tension
and one mounting.

**Models.** With labels, a supervised classifier becomes legitimate:

- **Random Forest** first. It is the right baseline: it handles the mixed feature scales in
  `feature_config.json` without preprocessing, gives per-class probabilities, and its
  feature importances are directly inspectable against the sensor that produced them.
- **XGBoost** second, for the accuracy gain, with early stopping on a grouped validation
  split. Expect it to beat Random Forest by a modest margin and to be more sensitive to
  class imbalance, so weight classes explicitly.
- Keep the same window geometry and the same feature functions from
  `ml/feature_engineering.py`, so the unsupervised and supervised systems stay comparable.

**Metrics that would then be honest**, reported per class and on session-held-out folds:
precision, recall, F1, the full confusion matrix, and detection lead time (how long before
a human noticed the fault did the model flag it). Report a spread across folds, not a
single number -- with three sessions the fold-to-fold variation will be wide, and hiding
that would repeat the mistake this project set out to avoid.

**What still would not be claimable**, even with this dataset:

- **Remaining useful life.** RUL needs run-to-failure data: components taken from healthy
  to actual failure, several times, with the failure time recorded. Induced faults that are
  reversed after 5 minutes cannot support it.
- **Failure probability.** A classifier's softmax output is a class score, not a
  probability that the machine will fail. Turning it into one needs calibration against
  observed failures.
- **Specific mechanical diagnosis beyond the induced classes.** A model trained on
  `HIGH_VIBRATION` induced by an eccentric mass has learned that eccentric mass, not
  bearing degradation. Claiming "bearing failure detected" would still be unsupported.

**Keep the unsupervised model.** The two do different jobs and should ship together: the
classifier recognises the fault modes it was taught, and the Isolation Forest catches
conditions that are unusual but belong to none of them. A supervised model asked about an
unseen fault will confidently return one of its six labels; the anomaly detector is what
stops that from going unnoticed.

---

## 4. Suggested order of work

1. Fix defects 1-4 above; verify with a 10-minute test recording and a re-run of
   `ml/data_inspection.py`. The duplicate-timestamp and segment-length rows in the report
   are the acceptance test.
2. Add motor current and a motor-shaft RPM source.
3. Record `NORMAL` across several speeds and loads. Retrain the existing unsupervised
   baseline on it -- that alone fixes the largest limitation in the current model, which is
   that it has only ever seen one operating point.
4. Record `RPM_INSTABILITY` (software-only, safest) and confirm the whole labelled pipeline
   works end to end on two classes before touching anything mechanical.
5. Record the remaining single-fault classes.
6. Record `COMBINED_FAULT`.
7. Train Random Forest, then XGBoost, with session-held-out evaluation.
