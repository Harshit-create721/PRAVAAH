Sensor bring-up

Wiring, flashing and verification for the conveyor joint-monitoring rig — in the order that isolates a fault to one thing at a time.

The dashboard never talks to a sensor. It only ever receives JSON on an MQTT topic. So “connecting a sensor” means making the ESP32 publish a field with the right name — which is why every sensor is independent, and why you bring them up one at a time rather than all at once.

Everything right of the dashed line is built and running. Your week is the left half.

01Network first

Prove the path with zero sensors

Do this before you wire anything. It separates a WiFi/broker problem from a sensor problem — and those two failures look identical if you tackle them together.

Flash the sketch with all six ENABLE_* flags left at 0, and only these set:

// firmware/beltguard_node/beltguard_node.ino
#define WIFI_SSID   "your-ssid"
#define WIFI_PASS   "your-password"
#define MQTT_HOST   "192.168.1.6"     // whatever start-beltguard.bat printed
#define CONVEYOR_ID "CV-01"           // must match server/config.js
#define NODE_ID     "esp32-drive-01"  // any unique name

Serial monitor at 115200 prints the ESP32's IP, then MQTT connect... ok. On the dashboard, Sensor nodes flips from NO NODE HAS ANNOUNCED ITSELF to a green esp32-drive-01 · LIVE — and every channel still reads NO SIGNAL.

That is exactly right: a live node with no live channels. Network proven, nothing faked.

If the node never appears

It is almost always one of three things, in this order of likelihood:

  • The firewall rules were never added (they need an Administrator prompt, once).
  • MQTT_HOST is the wrong address — a 169.254.x.x is a dead link-local adapter, not your LAN.
  • The ESP32 joined a different subnet. Common where the factory runs a separate guest WiFi.
netsh advfirewall firewall add rule name="BeltGuard MQTT" dir=in action=allow protocol=TCP localport=1883
netsh advfirewall firewall add rule name="BeltGuard HTTP" dir=in action=allow protocol=TCP localport=8811
02Wiring

One sensor, one flag, one reflash

Every sensor is three wires — VCC, GND, signal. Only the signal pin differs. Wire it, flip its single flag, reflash. That channel changes from NO SIGNAL to a number with a green LIVE badge within half a second, and nothing else on screen moves.

SensorSignal → pinPower Flag to setChannel that lights up
Speed — Hall A3144 or LM393 GPIO 275 V (VIN) ENABLE_SPEED belt_speed, motor_rpm
Joint marker, left edge GPIO 265 V (VIN) ENABLE_MARKER the joint table appears
Joint marker, right edge GPIO 255 V (VIN) ENABLE_MARKER_R L/R asymmetry rule
ADXL345 accelerometer GPIO 21 / 22 3.3 V only ENABLE_ADXL vibration_rms, kurtosis, crest
MLX90614 IR thermometer GPIO 21 / 22 3.3 V only ENABLE_MLX temperature, ambient
SCT-013 current clamp GPIO 34 via burden board ENABLE_CT motor_current_rms

GPIO 21 and 22 are the shared I²C bus. The ADXL345 and the MLX90614 both sit on it at different addresses, so they coexist on the same two wires — add 4.7 kΩ pull-ups to 3V3. Keep one common ground, starred at the ESP32. Avoid GPIO 6–11 (flash), and don't hang anything that pulls at boot on GPIO 0, 2, 12 or 15.

Hazard

The ADXL345 is a 3.3 V part — 5 V on its VCC destroys it immediately. The LM393 breakouts want 5 V, and their D0 output is open-collector, so it is safe to feed a 3.3 V GPIO through the pull-up.

The SCT-013 clamps around one conductor — never in series, never opened while the primary is energised. It needs a burden resistor and a 1.65 V bias divider before GPIO 34; wired raw it swings negative and kills the ADC. A qualified electrician does the panel-side work. Do not clamp anything on a VFD output.

If the factory won't allow a CT at all, ask whether the VFD already reports current over Modbus. That path is safer and better data, and the gateway can read it instead.

03The marker

The one sensor the project stands on

Speed and vibration are context. The marker is what turns a belt into a set of individually tracked joints — without it there is no per-splice history and no project.

OptionReads through≈ ₹Watch out
Hall A3144 + magnetdust, rubber, water60Recommended. Solid state, no contact bounce, survives a factory.
Reed switch + magnetdust, rubber, water80Magnet must be bonded, not bolted. Fast belts need a fast reed.
Slot / IR + reflective tagneeds line of sight50Dust and belt dressing kill it. Fine on a clean airport belt.
RFID tag + readerdust1200+Overkill for the MVP; worth a slide in the mining-pilot proposal.

Wire whichever you pick exactly where the slot sensor would go — the firmware treats them identically, with a 20 ms debounce in the ISR.

What happens on the first trigger

J01 appears in the joint table showing 1/20 under Baseline. Run the belt clean for twenty laps and it fills to 20/20, then locks. From that point every pass is compared against that joint's own history and the rules begin firing.

Before those twenty laps the dashboard deliberately shows no risk for the joint. It has nothing to compare against yet, and it will not pretend otherwise. The lock matters too: it is what stops a slowly degrading joint from dragging its own reference along with it.

The camera publishes vision carrying the same joint_id and lap. The gateway merges the two into one pass record — which is why the camera node must count laps the same way the ESP32 does, one increment per marker detection.

Three rules that keep the data honest

  • Omit what you did not measure. No 0, no -1, no null. Absent means absent, and the dashboard says so.
  • Out-of-range is rejected, not clamped. A clamped value is an invented value.
  • Field names are fixed. Anything else is ignored silently.
05Verify

Bring-up checklist

Each line is a thing you can see, not a thing you assume. Work down in order — a failure at any step is contained to that step.

Gateway running

Double-click start-beltguard.bat. It prints the IP for MQTT_HOST, then [broker] mqtt://0.0.0.0:1883.

Dashboard reachable

http://localhost:8811 shows NO DATA / no packet received yet and 15/15 channels at NO SIGNAL.

Node announces itself

All flags at 0. Sensor nodes shows the node LIVE, channels unchanged.

Speed reads true

Chalk mark and stopwatch over ten laps must agree with belt_speed within 2%. If not, fix PULSES_PER_REV and WHEEL_CIRC_MM before going further — everything downstream inherits this error.

Joint appears

Marker sensor triggers once per lap; J01 enters the joint table and the lap count climbs steadily.

Baseline locks

Twenty clean laps. The joint row reads 20/20 and rules start evaluating.

Geometry entered

Fill pulleyDiameterMm, gearRatio and beltLengthM in server/config.js. The amber banner clears and the slip rule switches on.

Controlled fault detected

On a spare joint only. An alarm fires carrying the numbers that produced it.

When a channel won't appear

Watch the Ingest panel — it is the fastest debugger on the rig. A field with a typo'd name is ignored silently; an implausible value is rejected with the reason printed: 

20:31:34  telemetry  belt_speed=9999: outside plausible range 0..12 m/s
20:31:27  telemetry  motor_current_rms=six point three: not a finite number

Node LIVE, channel NO SIGNAL, nothing being rejected? Then the field name doesn't match the contract.

06Discipline

The one rule that protects the whole dataset

Do not

Never flip an ENABLE_* flag to make the screen look fuller. The moment you publish a number no sensor produced, the joint baseline learns it — and every deviation calculation after that is measured against a fiction.

That is why all six flags ship at 0 rather than 1, and why a missing channel renders as NO SIGNAL rather than a plausible-looking zero.

The same applies to the bench harness in tools/. It exists to prove the topics route and the rules fire before hardware exists — it is a wire-protocol test, not a demo mode. It publishes under a bench-* node id and forces a red banner across the dashboard for as long as it runs. Kill it and delete data/beltguard.db before the first real capture, so bench rows never contaminate a baseline.

Safety

Lockout/tagout before mounting anything; never adjust a moving conveyor. Mount sensors, markers and cameras so they cannot become a snag, a projectile or a source of belt damage — bond tags outside the load-carrying area and clear of the splice itself.

Do not modify an airport or X-ray machine's radiation generator, curtains, interlocks or certified control chain. The alarms are decision support, not a safety system. Nothing here is wired to stop a machine, and it must not be until it has been validated, hazard-assessed and interlocked properly.
